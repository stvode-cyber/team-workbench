## 核心流程：01-03 三层架构定义

### 01 基础设施层（Infrastructure）— 全局选型 + 技术栈 + 架构模式

必须回答的 5 个问题：
1. 运行环境：裸机 / 容器（Docker / Kubernetes）/ Serverless？
2. 数据库：关系型（PostgreSQL / MySQL）/ 文档型（MongoDB）/ 键值（Redis）？为什么？
3. 外部依赖清单：要不要接短信 / 支付 / 推送 / 云服务？
4. 架构模式：单体 / 微服务 / 事件驱动 / BFF？匹配团队规模
5. 部署拓扑：单机 / 集群 / 多云？成本能承受吗？

每个选型必须带：成熟度 / 社区规模 / 学习曲线 / 性能上限 / 团队适配度

### 02 平台层（Platform）— 模块边界 + 单向依赖 + 接口契约

三大硬约束：
- 模块边界：每个模块一句话说清它管什么、不管什么
- 单向依赖：箭头方向只能上层→下层，出现反向 = 架构坏了，必须指出来
- 接口契约：模块间交互必须有明确的输入输出协议（函数签名 / API 定义 / 消息格式）

必查：
- 有没有跨模块直接访问数据库？（应该走接口）
- 有没有工具类被业务层反向依赖？（工具层应该最底层）
- 有没有循环依赖？（A 依赖 B，B 又依赖 A）

### 03 应用层（Application）— 数据模型 + API 规范 + 错误码

数据模型：
- 核心实体 ER 图（文字版或 Mermaid）
- 每张表的主键 / 外键 / 唯一约束
- 数据生命周期（创建 → 更新 → 归档 → 删除）

API 规范：
- URL 风格：RESTful（`/资源/{id}`）/ RPC（`/动作`）统一
- 请求体 / 响应体统一格式（code + message + data）
- 分页参数统一（page + size 或 cursor）
- 幂等性标注（哪些接口重复请求不会出问题）

错误码：
- 必须有统一错误码表（全局唯一）
- 至少覆盖：参数错 / 鉴权错 / 资源不存在 / 冲突 / 内部错
- 错误消息对用户友好，日志里带技术细节

## 技术选型检查清单

| 维度 | 必查项 |
|---|---|
| 团队 | 团队里有人会这个技术栈吗？没人愿意学 → 放弃 |
| 社区 | GitHub star ≥ 2000 + 近 6 个月有 commit |
| 替代 | 有没有更简单的办法能搞定 80% 的需求？（YAGNI） |
| 风险 | 闭源？付费？会不会卡脖子？ |
| 迁移 | 选了之后要换的话，迁移成本多大？ |

## 依赖方向图（文字版绘制规范）

```
上层 → 下层（箭头只能向下）
Application Layer（业务模块）
  ├─ 依赖 Platform Layer（框架 + ORM + 认证）
  │    ├─ 依赖 Infrastructure Layer（DB + Cache + MQ）
  │    │    └─ 不依赖任何上层
  │    └─ 不依赖 Application
  └─ 不被任何下层依赖
```

反向依赖检测：
- 搜 import / require / use 语句
- 搜函数调用路径
- 发现反向 → 立刻标红，不许"先这样吧"

## 必查表

| 场景 | 必须问 |
|---|---|
| 新项目 | 这个技术选型，团队里至少两个人愿意学吗？ |
| 改架构 | 现在有反向依赖吗？改了之后还会有吗？ |
| 加模块 | 这个新模块依赖谁？谁会依赖它？ |
| API 设计 | 这个接口幂等吗？重复调用会不会出问题？ |
| 技术栈迁移 | 迁移成本多大？值不值？ |
